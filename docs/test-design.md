# 接口自动化测试设计

本文件回答一个问题：**这套测试到底在守什么。**

三份文档分工：

| 文件 | 讲什么 |
|---|---|
| `architecture.md` | 代码怎么分层（路由 / 服务 / 数据） |
| `resilience.md` | 容错机制配了什么、为什么是这个值 |
| **本文件** | **怎么测、每层挡什么风险、哪里还没覆盖** |

现状：**25 条用例，25 passed**（`tests/` 8 个文件 + `conftest.py`）。

---

## 一、用例分层

### 1.1 分层表

| 层 | 文件 | 条数 | 一句话：在测什么 |
|---|---|---:|---|
| 探活 | `test_health.py` | 2 | 服务活着，且能自己应答 |
| 正常 | `test_ask_normal.py` | 4 | 四条正常路径都给出对的答案形状 |
| 缺参 | `test_ask_missing.py` | 3 | 少给字段，被拦住，**且按对理由拦住** |
| 非法 | `test_ask_invalid.py` | 4 | 给了值但不合法，两道关分别拦住 |
| 越界 | `test_ask_boundary.py` | 4 | 长度上限附近的四个点位 |
| 服务异常 | `test_ask_server_error.py` | 3 | 数据库拒绝我时，服务怎么表态 |
| 幂等 | `test_ask_idempotency.py` | 3 | 同一个请求重复发，只算一次 |
| 重试 | `test_retry_unit.py` | 2 | 重试几次、什么时候放弃 |

合计 **2 + 4 + 3 + 4 + 4 + 3 + 3 + 2 = 25**，与 `pytest tests --collect-only -q` 输出的 `25 tests collected` 一致。

### 1.2 为什么「探活」单列一层

清单给的口径是七层（正常 / 缺参 / 非法 / 越界 / 异常 / 幂等 / 重试），那七层只装得下 23 条。多出来的 2 条是 `/health`。

单列而不并进「正常层」，理由是它测的东西性质不同：

- 正常层那四条测的是 **`/ask` 的业务语义**——有没有查到、答案对不对、历史能不能读回来
- `/health` 测的是 **进程有没有活着**，它压根不碰数据库

这个区别有实际用处：服务异常层里那条 `test_health_200_when_db_auth_fails` 就是在「数据库全挂」的情况下断言 `/health` 仍然返回 200。**如果 health 混在正常层里，这条跨层的对照关系就看不出来了。**

### 1.3 一个请求进来，各层分别拦在哪一步

```
POST /ask
  │
  ├─[1] Pydantic 校验 AskRequest.question        ← 缺参层、非法层（一半）
  │        缺字段 / 类型不对 → 422
  │
  ├─[2] 幂等查重 _CACHE                          ← 幂等层
  │        命中 → 直接返回上次结果，后面一步都不走
  │
  ├─[3] 业务校验 req.question.strip() == ""      ← 非法层（另一半）
  │        空串 / 纯空格 → 400
  │
  ├─[4] retry_call(do_query)                     ← 服务异常层、重试层、越界层
  │        MySQL 拒绝 → 1045 立刻抛 / 2003 重试 3 次
  │
  ├─[5] db.add(AskLog(...)) + commit()           ← 幂等层（数据库兜底）／**未覆盖**
  │        request_id 撞唯一索引 → IntegrityError → 500
  │
  └─[6] 组装响应 → 200
```

这张图是分层的依据：**每一层守的是流程上的一个卡口，不是按文件名分的。** 所以同一层的用例可以落在不同文件里（比如「非法」层一半在 Pydantic、一半在 service），同一个文件里也可以测两个卡口。

### 1.4 口径账（和清单不一致的地方）

清单（2026-11-19 调整版）写的是「非法组 5 条 + 越界组 3 条」，实际落地是 **非法 4 条 + 越界 4 条**，总数仍是 8 条、总数仍是 25：

| 口径 | 非法 | 越界 | 合计 |
|---|---:|---:|---:|
| 清单预期 | 5 | 3 | 8 |
| 实际落地 | 4（400 组 2 + 422 组 2） | 4（4999 / 5000 / 5001 / 10000） | 8 |

差异来源：原来那条「10000 字符」的用例落在 `test_ask_invalid.py` 里，重构时**挪进了 `test_ask_boundary.py`**——因为它跟 4999/5000/5001 是同一件事（长度），放在非法组里会和「类型错」混在一起，说不清这一层到底在守什么。

**条数没变，归属变了。** 以后核对口径按这张表，不要按清单原文字。

## 二、每层挡什么风险

### 2.1 探活层（2 条）

| 用例 | 断言 |
|---|---|
| `test_health` | 200 + `{"status": "OK"}`（用裸 `requests`，不走 `ApiClient`） |
| `test_health_via_client` | 同上，走 `ApiClient.session` |

**在测什么**：服务起来了没有。

**为什么留两条**：一条走裸 `requests`、一条走 `requests.Session`，两条都过才说明「连接能被复用、也能被新建」。它同时也扮演 `conftest.py` 里 `server` fixture 的「等端口就绪」探针——服务没起来时这两条先红，不会一上来就一堆 `ConnectionError`。

**风险**：这条防线极薄但极重要。`/health` 不碰数据库，所以它是**唯一能在数据库全挂时依然给出健康信号**的接口，负载均衡和 K8s 探活全靠它。

### 2.2 正常层（4 条）

原话是「防止已收录的题目返回错误、没查到题目返回错误、输入问题有特殊字符返回错误、查询记录返回错误」。这四句是**愿望**，落不到断言上，改成正面表述就是四条正常路径：

| 用例 | 覆盖的路径 | 关键断言 |
|---|---|---|
| `test_ask_normal` | **命中**：题库里有这道题 | `matched is True` + 键集合 `{answer, common_mistake, matched, question}` + `answer` 是非空字符串 |
| `test_ask_not_found` | **未命中**：题库里没有 | `matched is False` + 键集合 `{matched, answer}` + `answer == "题库暂未收录该题"` |
| `test_ask_special_chars` | **脏输入**：`直角三角形 <&% 测试` | 200 + `matched is False` |
| `test_history` | **回读**：刚提交的提问能从 `/history` 查到 | 200 + 是 list + 里面含这条 question + 元素键集合 `{id, question, matched, created_at}` |

**在测什么**：不只是「别报错」，是**两条分支各自的返回形状**。

命中与未命中返回的是**两套不同的键集合**——命中带 `common_mistake`，未命中只有 `{matched, answer}`。这是接口契约里最容易被后续改动破坏的地方（比如统一返回结构时顺手把 `answer` 改成 `null`），所以两条都断言了 `set(body.keys()) == {...}` 而不只是断言 `matched`。

**特殊字符那条为什么断言 `is False`**：

服务端查库用的是 `Question.question.contains(keyword)`，翻译成 SQL 就是 `LIKE '%直角三角形 <&% 测试%'`——**整串比对，不分词**。所以只要那个 key 不存在，结果必然是 `False`。

原先这条只写了 `assert "matched" in body` 和 `isinstance(body["matched"], bool)`，那是**结构检查**：字段在不在、类型对不对，值是什么都放行。改成 `is False` 之后变成**结果检查**。

`is` 比 `==` 严：`0 == False` 为真，`0 is False` 为假。用 `is False` 就不会被 `0`、`""`、`[]` 这类假值蒙过去。

**副作用提醒**：变严之后，如果将来服务端加了分词、这条输入真的命中了题库，用例会红。**那不是误报，是接口契约变了**，得回来改断言。

### 2.3 缺参层（3 条）

三条都返回 422，但**拦的理由不一样**：

| 请求体 | `detail[0]["type"]` | `detail[0]["loc"]` | 说明 |
|---|---|---|---|
| `{}` | `missing` | `["body", "question"]` | 请求体在，字段没给 |
| `{"question": null}` | `string_type` | `["body", "question"]` | 字段给了，值是 `None`，不是字符串 |
| 不传 body | `missing` | `["body"]` | 整个请求体都没给 |

**在测什么**：不只是「返回 422」，是**它按哪个理由拦的**。

`loc` 与 `type` 这两项合起来是一句话：「哪一层、哪一格、什么毛病」。只断言状态码会被一种情况骗过——**服务因为别的原因返回 422**（比如上了一个全局异常处理器把 400 也改写成 422），状态码对、案子错。

**为什么 `null` 被判成 `string_type` 而不是 `missing`**：Pydantic 的规矩是「显式给了值就按类型校验，没给才算缺」。`null` 是给了值的，只是这个值不是字符串。

### 2.4 非法层（4 条）

两个参数化函数，各 2 条数据：

| 函数 | 数据 | 断言 |
|---|---|---|
| `test_empty_question` | `""`、`"   "` | **400** + `{"error": "question不能为空"}` |
| `test_question_type` | `123`、`["a"]` | **422** + `detail[0]["type"] == "string_type"` |

**在测什么**：进到服务里的两道关分别起作用。

原话的判断是对的：**空格或空值能过请求体 string 的关，过不了业务判空的 400 关；列表和数字过不了 `str` 的关，被 Pydantic 拦住报 422。**

两口关是**串联有先后**的，顺序不能反：

```
请求体 → [Pydantic: 是不是 str?] → [service: strip 完还有内容吗?] → 查库
              ↓ 不是str                     ↓ 是空的
            422                            400
```

数字 `123` 和列表 `["a"]` **永远走不到判空那一步**，因为第一关就拦下了。这也是为什么这一层必须用 422 和 400 两种状态码分别断言——只测一种，另一道关等于没测。

一句话记住这层的边界：**Pydantic 能校验形状，校验不了含义。**「是不是字符串」它管得了，「是不是有意义的题目」它管不了。

**一个已经踩过的坑**：参数里 `"123"`（带引号）和 `123`（不带）是两回事。带引号是字符串，会被判空那关放行、走进查库，返回 **200**，不是 422。写数据时别手滑加引号。

### 2.5 越界层（4 条）

一个参数化函数，四组数据：

| 数据 | 当前实际 | 加了 `max_length=5000` 之后应当 |
|---|---|---|
| 4999 字 | 200 | 200 |
| 5000 字 | 200 | 200（正好等于上限，放行） |
| 5001 字 | 200 | **422** |
| 10000 字 | 200 | **422** |

每条的断言都是完整的四条：`200` / `matched is False` / 键集合 `{matched, answer}` / `answer == "题库暂未收录该题"`。**不是只剩状态码**——那样等于退化成「能通就行」，看不出来返回到底对不对。

**当前处境的实话**：服务**现在没有长度上限**，所以四条全是 200，`test_ask_boundary.py` 文件头第 1—2 行的注释就是在说这件事——**先锁现状，不是锁正确行为**。

**这层的真实价值是「替未来的自己记账」。** 四组数据被 `5000` 这个数锚住了，它的意义只在「将来加了上限」那一刻才显出来：

- 上限要是设成 **500**，四条全变 422，「刚好通过」的边界点消失，这层白测；
- 上限设成 **5000**，只有后两条变 422，前两条仍然绿——**用例替你把 4999 / 5000 / 5001 这三个点的语义钉死了**。

所以加限制时改的是**后两条的断言**（200 → 422），另外两条一个字不用动。如果到时候四条一起变红，说明上限值设错了，不是用例错了。

**断言位置的选择**：长度限制要加在 Pydantic 的 `Field(max_length=5000)` 上，不是写在 service 里判 `len()`。理由是**最靠入口的地方拦**——超长文本不必进 service、不必占着连接池和一次查库开销。这也是 422（框架校验）和 400（业务校验）的分界。

### 2.6 服务异常层（3 条）

| 用例 | 断言 | 在测什么 |
|---|---|---|
| `test_ask_500_when_db_auth_fails` | 500 + `elapsed < 6` | 库拒绝我 → 500，且**没有卡死** |
| `test_history_500_when_db_auth_fails` | 500 | `/history` 同样如实报错 |
| `test_health_200_when_db_auth_fails` | 200 + `{"status": "OK"}` | 库全挂时探活仍然通 |

**怎么造的故障**：`conftest.py` 里 `bad_db_server` 起一个 **8001**，`env={**os.environ, "DB_PASSWORD": "wrong_password"}`。请求打进去，MySQL 回 **1045**，服务返回 500。

**为什么另开 8001，不在 8000 上改密码**：

| 做法 | 代价 |
|---|---|
| 8000 中途换密码 | 要关服务 → 端口等 TIME_WAIT（会报 `10048`）→ 用坏密码重开 → 跑完再改回来；**并且引入顺序依赖**，不能一次跑完 |
| 8000 + 8001 并存 | 多起一个进程，一次跑完 |

选后者。关键在**顺序依赖**：测试的基本原则是每条用例都能单独跑、单独通过。一旦依赖「前面那条跑过没有」，单跑绿、整体跑红，排查时先怀疑代码，其实是顺序问题；上 `pytest-xdist` 并行直接崩。

**8000 的服务改设置为什么影响不到**：服务进程一启动就把配置读进内存了，之后在测试端改 `os.environ`、改 conftest 里的变量，对已经在跑的进程毫无作用——**两个进程，各管各的**。真要换配置只有一条路：关掉重开。所以故障得靠「另起一个进程」来造。

一句话：**造故障要开副本，别在主线路上动手。**

**`elapsed < 6` 守的是什么**：1045 是「对面明确拒绝」，建连立刻失败（实测 0.02 秒），完全不走 `connect_timeout=5`。所以这个 6 秒的上界是**防另一种病变**——万一哪天这个错误被误判成可重试，会变成 3 次 × 建连 + 2 次 sleep，耗时就上去了。**它是 fail-fast 的守门员**，详见第四节。

**不是「连接返回 500」，是「服务返回 500」**：1045 是 MySQL 的错误码，事故发生在服务内部；500 是服务对外的表态。这两件事一个是因、一个是果，不能混着说。

### 2.7 幂等层（3 条）

| 用例 | 做法 | 断言 |
|---|---|---|
| `test_same_request_id_writes_once` | 同一个 `rid` 连发两次相同问题 | **库里该 rid 的行数 == 1** + 两次都 200 + 两次响应完全相同 |
| `test_different_request_ids_write_two_rows` | 两个不同 `rid` 发同一问题 | 各自行数 == 1 + 都 200 |
| `test_no_header_generates_distinct_id` | 不带 header 连发两次 | 库里两行 + 两个 `request_id` 都非空 + **两者不相等** |

**在测什么**：**副作用**，不是响应。

这是这一层最重要的一条方法论：**幂等关心的是副作用，副作用落在数据库里，不落在响应里。** 只看响应是不够的——两次返回一模一样，完全可能背后写了两行。所以每条用例的核心动作都是去 `AskLog` 表里数行数：

```python
db = SessionLocal()
n = db.query(AskLog).filter(AskLog.request_id == rid).count()
assert n == 1
```

**`r1.json() == r2.json()` 是辅助断言，不是主断言。**

**第三条里两个容易漏的细节**：

1. **不带 header 会不会被 Pydantic 拦住**——不会。`X-Request-ID` 声明成 `Header(default=None, alias="X-Request-ID")`，**有默认值就可选**。对照 `AskRequest.question: str` 没有默认值，所以必填，缺了才 422。Pydantic 的规矩一句话：**有默认值的可以缺省，没默认值的必填。**
2. **服务端自己造的 `request_id` 没有 `test-` 前缀**，`clean_ask_logs`（只删 `request_id LIKE 'test-%'`）删不掉它。跑十次就有二十条垃圾留在库里。所以这条用例**自己收拾**：断言做完手动 `delete()` + `commit()`。

**这一层的诚实边界**：`_CACHE` 是进程内字典，不是数据库。服务重启就忘、多进程各存各的、扩容多机直接失效。**用的唯一索引是持久化的**，所以重启后能查到「这个 id 来过」，但没有旧答案可返回。要让重启后仍能直接返回旧结果，得把结果本身存起来（Redis，或 `ask_logs` 加一列 `answer`）。

### 2.8 重试层（2 条）

| 用例 | 做法 | 断言 |
|---|---|---|
| `test_retry_succeeds_on_second_attempt` | 假函数 `flaky`：第 1 次抛 2003，第 2 次返回 `"OK"` | `result == "OK"` + `calls == 2` + 只有 **1** 条「次重试」日志 + 没有「最终失败」 |
| `test_retry_gives_up_after_max_attempts` | 假函数 `always`：每次都抛 2003 | `pytest.raises(OperationalError)` + `calls == 3` + **2** 条「次重试」日志 + 出现「最终失败」 |

**为什么不碰接口**：原话是「我们制造了假函数来代替访问接口，假函数可以控制什么时候报错，用真接口控制不了」。这是对的，而且是这一层的全部理由——

真接口造不出「第一次失败、第二次成功」这种**精确时序**；真接口也不能保证抛的一定是 `2003`（可能是 1045、1064 或者根本没有异常）。**测「重试次数」这件事，必须把「什么时候抛、抛什么」拿在自己手里。**

**几个数字为什么是 2 和 3**：`max_retries=2` 走的是 `range(max_retries + 1)`，也就是 `range(3)`，**一共调 3 次**：

- 第 1 次：进入 except → 可重试 → `attempt(0) != max_retries(2)` → 打「第1次重试」，sleep
- 第 2 次：进入 except → 可重试 → `attempt(1) != 2` → 打「第2次重试」，sleep
- 第 3 次：进入 except → 可重试 → `attempt(2) == 2` → 打「最终失败」 → `raise`

所以「次重试」日志是 **2 条**、函数调用是 **3 次**。第三个 `attempt` 不再重试，而是放弃。数错这个的关系，断言就会写反。

**`Exception(2003, ...)` 是干什么的**：`OperationalError` 的 `.orig` 要带着原始错误码，`is_retryable` 靠 `exc.orig.args[0] in {2003, 2006, 2013}` 判断。手工造这个异常时，第三个参数就是拿来伪造 `exc.orig.args[0]` 的——**造得不对，`is_retryable` 会判「不可重试」，这条用例连重试分支都进不去。**

`delay=0` 是为了不真等 0.5 秒 × 2。

`calls` 用字典 `{"n": 0}` 而不是外层整数，是因为闭包里给整数 `+= 1` 在 Python 里绑不上去（会变成局部变量），字典的键可以。

**这一层的已知薄弱点**：`with pytest.raises(OperationalError)` **只认类型，不认里面的错误码**。1045 同样是 `OperationalError`，同样会被接住，用例同样是绿的。所以如果哪天代码出 bug 把 1045 也加进白名单，这两条发现不了。

补法：

```python
with pytest.raises(OperationalError) as excinfo:
    retry_call(always, max_retries=2, delay=0)

assert excinfo.value.orig.args[0] == 2003
```

## 三、参数化省下了什么

### 3.1 重构前后对照

| 文件 | 改前 | 改后 |
|---|---|---|
| `test_ask_invalid.py` | **5 个函数**（空/空格/数字/列表/10000 字各一个），断言块 5 份 | **2 个函数 4 条数据**，断言块 2 份 |
| `test_ask_boundary.py` | **3 个函数**（4999/5000/5001 各一个），断言块 3 份 | **1 个函数 4 条数据**，断言块 1 份 |

### 3.2 省的不是字数，是「改一处漏三处」的风险

这一点必须说清：**参数化的收益不在代码短，在断言只有一份。**

改前是「一个函数一个数据点」，同一个断言写 4 遍。想加严一条断言（比如给越界四条都补上 `answer == "题库暂未收录该题"`），得手动改 4 个地方，漏一个就变成「三条严、一条松」——**而漏掉的那条照样是绿的，你不会发现。**

改后是一条断言管四组数据，加严一次，四条同时变严。

### 3.3 加一条数据只要一行

```python
@pytest.mark.parametrize("body,rid",[
    ("直"*4999,"test-boundary-1"),
    ("直"*5000,"test-boundary-2"),
    ("直"*5001,"test-boundary-3"),
    ("直"*10000,"test-boundary-4"),
    ("直"*50000,"test-boundary-5"),   # ← 新增就这一行
])
```

不用抄函数签名、不用抄 4 条断言。

### 3.4 参数进了报告，能单独定位到哪一条

用例 ID 是这样的：

```
tests/test_ask_boundary.py::test_too_long_question[body2-test-boundary-3]
```

方括号里是参数名和值。**所以 `rid` 也被放进了参数表**——它本身不参与断言逻辑，纯粹是为了让每条用例在 `-v` 输出和 Allure 报告里有可区分的名字。没有它，四条会是 `[body0] [body1] [body2] [body3]`，红了不知道是哪一组。

Allure 的 `result.json` 里也确实记着：

```json
"parameters": [
  {"name": "body", "value": "'直直直…（5001 个字）'"},
  {"name": "rid",  "value": "'test-boundary-3'"}
]
```

### 3.5 踩过的三个坑（写参数化一定会遇到）

1. **参数名必须写在同一个字符串里，用逗号分隔**：`("body, rid", [...])` 是三个位置参数，会报 `TypeError: string indices must be integers`。正确是 `@pytest.mark.parametrize("body, rid", [...])`。
2. **装饰器后面要逗号**：`@pytest.mark.parametrize("body,rid"[` 少了逗号，报 `TypeError: string indices must be integers`，Python 自己会给一句 `SyntaxWarning: ... perhaps you missed a comma?`——**看到这句警告就是这里。**
3. **函数签名要把参数接住**：`def test_xxx(api_client, body, rid)`。不接的话参数照样注入，但函数体只能用写死的老变量，四条数据跑出来会一模一样。

另一个更隐蔽的：**函数体改名要改全**。把局部变量从 `body` 改成 `rsp` 时，如果只改了赋值那行、后面三行还写 `body["matched"]`，会报 `TypeError: string indices must be integers`——因为此时 `body` 已经变成测试参数（字符串），不是响应字典。

## 四、分层与降级

这一节讲的是测试和容错机制的接口：**容错给了什么承诺，测试怎么验它；哪些承诺现在还没验。**

### 4.1 fail-fast：不该重试的，一次都别试

`retry.py` 的白名单是 `{2003, 2006, 2013}` + 池超时。**1045 不在里面，遇到就立刻 `raise`，一次都不重试。**

这是有意的设计：**密码错了，等到天亮也不会对。** 重试只会把用户等待从几十毫秒拖到约 1.1 秒（3 次 × 几十毫秒 + 2 次 sleep），还多占着连接池和线程。

测试怎么验这个承诺：`test_ask_500_when_db_auth_fails` 断言 `r.elapsed.total_seconds() < 6`。

**但这道闸有边界，得说清它拦得住什么、拦不住什么：**

| 如果出了什么问题 | 耗时表现 | 用例结果 |
|---|---|---|
| 正确行为：fail-fast | 约 0.02 秒 | 绿 |
| 请求被挂住不返回 | 超过 6 秒 | **红** |
| 1045 被误加进白名单 | 3 × 0.02 秒 + 2 × 0.5 秒 ≈ **1.1 秒** | **绿——抓不住** |
| 2003 那种真正的干等 | 3 × 2 秒 + 1 秒 ≈ 7 秒 | 红（但本用例走不到这个分支） |

原来这里写的是「1045 被误加进白名单 → 十几秒 → 红」，**那是错的**：1045 建连几十毫秒就返回，重试三次加起来约 1.1 秒，仍小于 6。6 秒这道闸抓的是「一次真正的干等」（2003，每次约 2 秒），抓不住「1045 被误判」。

**这条真正该被锁住的地方不在接口层，而在单元层**：一条 `assert is_retryable(OperationalError(1045, ...)) is False` 就能钉死。现在 25 条里没有这一条——这是真实缺口，已记进 `stage1-review.md` 的已知限制。

**为什么 fail-fast 值钱**：数据库真挂时，每个还在重试的请求都继续占着连接池和线程。并发一高，重试会把「一个服务慢」放大成「整个服务被自己的重试压垮」——这就是雪崩。次数和间隔是阀门，白名单是阀门上的筛子。

### 4.2 重试单测为什么在进程内做，不打接口

已经在 2.8 说过，这里补上「代价」：

| 做法 | 好处 | 代价 |
|---|---|---|
| 假函数（现在的做法） | 精确控制「第几次失败、抛什么码」；毫秒级；不依赖服务 | 不验 `retry_call` 真的接进了 `/ask` 这条路径 |
| 打真接口 | 端到端 | 造不出精确时序；只能靠改端口让连接失败，慢且脆 |

**这个代价是真实的**：现在这两条单测证明「`retry_call` 本身会重试 3 次」，**不证明「`/ask` 真的调了 `retry_call`」**。那半截证据在 `resilience.md` 的实测记录里（2026-11-17 把库指向没监听的 3307，日志里出现「第1次重试」「第2次重试」「最终失败」，总耗时 13.26 秒）——**但那是手工脚本，不是仓库里的用例。**

### 4.3 超时：接口层还没验（明确的欠账）

**现状：这 25 条里，没有任何一条覆盖「数据库不响应时，接口会在 5 秒内返回，而不是挂死」。**

这是这一层最清楚的缺口。`resilience.md` 里做过一次，配置是：

- `connect_args={"connect_timeout": 5}`（建连最多 5 秒）
- `pool_timeout=5`（从池里排队最多 5 秒）

2026-11-17 用临时脚本（`sys.path` 注入 + 把 `database.SessionLocal` 换成指向黑洞地址 `10.255.255.1` 的 engine + 起 8001）测到：

| 请求 | 状态码 | 耗时 |
|---|---|---|
| `POST /ask`（库指向黑洞） | 500 | 5.13 秒 |
| `GET /health`（同时发） | 200 | 0.037 秒 |

结论成立：**超时配置在接口层确实生效，请求没有挂死；一个接口卡住不等于全站卡住。**

**但它是脚本，不是用例。** 没进仓库意味着：以后有人改了 `connect_timeout`（比如从 5 改成 30），没有任何东西会变红。

补救路径（还没做）：把这个方法搬进 `conftest.py`，做成第三个 fixture——起 8002，`database.SessionLocal` 在 `import main` **之前**就被换掉（`main.py` 里是 `from database import SessionLocal`，导入顺序决定它拿的是哪一个），然后一条用例断言 500 + `elapsed < 6`。

**注意这两条超时的语义不同，别混**：

- `connect_timeout` 管「连不上」（对面沉默、黑洞、TCP 无应答）
- `pool_timeout` 管「排不上队」（池子被占满）

`connect_timeout` 只在**对面不响应**时才等满上限；**对面明确拒绝**时立刻失败。所以 1045 那条用例（0.02 秒）根本走不到 5 秒，别拿它当超时的证据。

另外别忘了那个同名不同源的坑：`retry.py` 里 `TimeoutError as PoolTimeout` 抓的是 `sqlalchemy.exc.TimeoutError`（池超时），**和 Python 内置的 `TimeoutError` 没有继承关系**。写 `except TimeoutError` 时先想清楚抓的是哪一个。

### 4.4 降级：现在没有

**这套服务没有降级逻辑。** 数据库挂了就是 500，没有缓存兜底、没有备用数据源、没有降级返回。

所以「对外怎么表态」这件事，现在只有一个答案：**500。**

理想的分工是这样：

| 故障性质 | 该回什么 | 为什么 |
|---|---|---|
| 瞬时抖动，重试后恢复 | 200（用户看不到） | 已自愈，不必打扰调用方 |
| 数据库不可用但进程活着 | **503** + `Retry-After` | 明确告诉调用方「我这边临时不行，等会儿再来」，而且**这个错误可以重试** |
| 代码 bug、未捕获异常 | 500 | 事故，没有可操作的指引，不能吐内部细节（堆栈含 SQL、表名、密码字段） |

一句话：**500 是事故的下场，503 是设计的结果。** 现在的实现里，所有异常都落到 500，包括「其实只是数据库暂时不可用」这种情况——调用方拿到 500 会以为是我把你的请求写错了。

**测试侧的对应关系**：服务异常层那三条现在断言的 500，**就是把现状锁住了**。以后服务改成「库不可用回 503」，那两条要改成断言 503 —— 那时候改断言不是「测试坏了」，是**契约变了，测试跟上**。

**「进程活着」和「业务能干活」是两件事**：库全挂时，登录、查题、写日志全都办不到，业务上确实没价值。但进程活着有三样具体用处——

1. `/health` 还能应答，负载均衡和 K8s 靠它判断要不要把这个实例摘掉，不用等用户投诉
2. 日志还在写，1045 那次的原样错误、`request_id`、耗时都留在日志里，排障有线索
3. 还能回 503，让调用方知道「别猛重试，我这边在修」

这三件事都要求进程没死。所以 500 之后「下一个请求还能不能成」的答案是：**看情况。** 瞬时故障的，下一个可能就绿了；配置错了的，下一个照样 500，直到有人改配置重启。

### 4.5 三个机制在测试里的对应位置

| 机制 | 靠哪条用例守 | 覆盖程度 |
|---|---|---|
| 超时（等待上限） | — | **未覆盖**（只有 `resilience.md` 的手工脚本） |
| 重试（次数与放弃） | `test_retry_unit.py` 2 条 | 单元级覆盖；`/ask` 是否真接了 retry 未覆盖 |
| 幂等（重复只算一次） | `test_ask_idempotency.py` 3 条 | 接口级 + 库内行数核对，覆盖充分 |
| fail-fast（不该重试的不重试） | `test_ask_server_error.py` 的 `elapsed < 6` | 间接覆盖（靠耗时推断） |
| 唯一索引兜底（`IntegrityError`） | — | **未覆盖**（并发撞库会 500） |

## 五、报告怎么看

### 5.1 两段式的工具，别以为是装错了

| | `allure-pytest` | `allure` 命令行 |
|---|---|---|
| 是什么 | pytest 插件（Python 包） | Allure 官方命令行工具（Java 程序） |
| 用什么装 | `pip` | `npm`（`npm install -g allure-commandline`） |
| 干什么 | 跑测试时把结果写成 json | 读那些 json，渲染成网页 |

`pip install allure-pytest` 装完，敲 `allure --version` 照样不认——**装的不是同一半。** 前半段（生成 json）已经够清单验收。

### 5.2 跑法

```powershell
cd D:\Code\fastapi-learn
D:\anaconda\envs\fastapi_learn\python.exe -m pytest tests --alluredir=./report --clean-alluredir
```

- `--alluredir=./report`：结果写进 `report/`
- `--clean-alluredir`：**跑之前先清空目录**

不加 `--clean-alluredir` 的话，每次跑都往里叠加，`report/` 会越积越多，最老的用例记录会一直混在新结果里，报告上的「历史」全是假的。日常跑一律带上这个参数。

`report/` 应该进 `.gitignore`——它是生成物，不是源码。

### 5.3 目录里到底有什么（实测）

| 项 | 实测值 |
|---|---|
| 文件总数 | **123** |
| 总量 | **140 KB** |
| `*-result.json` 份数 | **25**（每条用例一份） |
| `*-container.json` | 分组（suite / fixture 层级） |
| `*-attachment.txt` | 用例的 `log` 和 `stdout` 抓取 |

单个 `result.json` 的真实字段：

| 字段 | 内容 |
|---|---|
| `name` | 用例 ID，含参数，如 `test_too_long_question[body2-test-boundary-3]` |
| `status` | `passed` / `failed` / `broken`（异常）/ `skipped` |
| `parameters` | **参数化的每一组参数和值** |
| `start` / `stop` | 毫秒时间戳，相减就是耗时 |
| `fullName` / `testCaseId` / `historyId` | 定位与历史趋势用 |
| `labels` | `parentSuite` / `suite` / `host` / `framework` / `language` / `package` |
| `attachments` | `log`、`stdout` 两份文本 |

### 5.4 为什么 140 KB 里有大半是「直」字

最大的四个 `result.json`：

| 大小 | 对应用例 |
|---|---|
| 31046 B | `test-boundary-4`（10000 字） |
| 16049 B | `test-boundary-3`（5001 字） |
| 16046 B | `test-boundary-2`（5000 字） |
| 16043 B | `test-boundary-1`（4999 字） |

四个加起来约 **79 KB，占 140 KB 的 56%**。

**原因是参数值被原样写进了 json。** 那 4 组数据的 `body` 就是几千个汉字，一个不落地存进了 `parameters`。

这不是 bug，但值得记住两件事：

1. **参数化的数据会进报告**，别往参数里塞超大字符串（比如整个文件内容），否则报告体积会失控；
2. **`report/` 不进 git** 这件事因此更重要——一次跑生成 140 KB，跑十次不清就是 1.4 MB 的「直」字进仓库。

### 5.5 装了命令行之后

```powershell
npm install -g allure-commandline
cd D:\Code\fastapi-learn
allure serve .\report
```

会起一个本地网页。**这一步是加分项**，清单验收（「至少确认 `report/` 下有 json」）已经达成，跳过不算欠账。

### 5.6 能口述的话

**为什么用 `parametrize` 而不是复制粘贴用例**：复制粘贴会让同一个断言存在多份，改一处漏三处，而漏掉的那条照样是绿的；参数化把断言收成一份，加数据只加一行，用例 ID 里还带着参数值，红了能一眼定位到哪组数据。

**Allure 报告里能看到哪些信息**：用例 ID（含参数）、通过/失败/异常/跳过四种状态、每组参数的实际取值、开始与结束时间（相减得耗时）、日志和标准输出、以及按文件/包/主机/框架分的层级标签。用命令行渲染出来还会多出历史趋势和用例分组树。

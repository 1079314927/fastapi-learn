## 一、做了什么

**服务**：FastAPI + MySQL，三个接口。`POST /ask` 接收题目、查题库、命中返回解题步骤和常见错因、未命中返回「题库暂未收录该题」，每次提问落一条 `ask_logs`；`GET /history` 取最近 20 条倒序；`GET /health` 不碰数据库，只报进程活着。题库 5 条，覆盖一元二次方程、分式方程、二次函数、勾股定理、不等式组。

**容错**：三道护栏分开做。超时 `connect_timeout=5` 管「连不上」、`pool_timeout=5` 管「排不上队」；重试 `retry_call` 最多 2 次、间隔 0.5 秒，只对 `2003 / 2006 / 2013` 和池超时生效，1045 这类错误一律不重试；幂等靠 `X-Request-ID`，进程内 `_CACHE` 查重在 `db.add` 之前，数据库侧再用 `ask_logs.request_id` 唯一索引兜底。

**日志**：结构化输出，每条带 `request_id` / `path` / `method` / `duration_ms` / `status`。选「拼 JSON 字符串」而不是 logging 的 `extra`，因为 `extra` 要改全局格式串，会让没带 `request_id` 的日志（重试、health、SQL 回显）全部报错。

**测试**：25 条（接口 23 + 单元 2），8 个测试文件。按卡口分层而不是按文件名：探活 2、正常 4、缺参 3、非法 4、越界 4、服务异常 3、幂等 3、重试 2。全部通过，最近一次本地运行 `25 passed in 1.97s`。

**CI**：GitHub Actions，push 到 main 自动跑。MySQL 用 service 容器起，`DB_PASSWORD=test_password`；先 `init_db.py` 建表、再 `seed.py` 灌数据、最后从仓库根 `python -m pytest`。最近一次运行 success（`b81e330`，run 45144708935）。

**文档**：`README.md`（写给陌生人的入口）、`architecture.md`（分层与职责）、`resilience.md`（三道护栏的配置与实测）、`test-design.md`（每条用例守哪个卡口）、`progress.md`（仓库进度台账）、`day1-notes.md`（按天复盘）。

## 二、卡在哪，怎么解决

### 1. 2003 和 1045 是两回事

两个错误码看着都像「连库失败」，实际分属两个阶段——第 16 天用两组地址实测才分清楚：

| 情况 | 错误码 | 发生了什么 | 每次耗时 |
|---|---|---|---|
| 端口不通 / 服务没起 | **2003** | TCP 都连不上，客户端干等 | 约 2.05 秒 |
| 密码错 | **1045** | TCP 已连上，MySQL 立刻回「密码不对」 | 几十毫秒 |

解决：`is_retryable` 用错误码白名单 `{2003, 2006, 2013}` + 池超时。1045 不在里面，遇到直接上抛——密码不会因为等两秒就变对。

留下的证据：接口层用错误密码另起 8001，断言 500 + `elapsed < 6`；重试逻辑用假函数单元测两条——第一次失败第二次成功（`calls == 2`、1 条重试日志、无「最终失败」），一直失败时三次放弃（`calls == 3`、2 条重试日志、最后 `raise`）。两条都传 `delay=0`，单测不用真等。

**但 `elapsed < 6` 证明不了 fail-fast，这一点必须写清楚。** 1045 每次几十毫秒，就算真被误加进白名单，3 次尝试 + 2 次 sleep 也只有约 1.1 秒——**仍然小于 6，用例照样是绿的。** 这道闸抓的是 2003 那种真正的干等（按单次 2.05 秒推算，3 次约 7.2 秒；若走 `localhost` 双地址，实测单次约 4.1 秒、总约 13.5 秒），抓不住 1045 被误判。

（`test-design.md` 4.1 那张表里「1045 被误加进白名单 → 十几秒 → 红」这一格原来是错的，已按第 16 天实测的单次耗时（2003 约 2.05 秒、1045 几十毫秒）重新算过改正。）

**还有一个真实缺口**：25 条里没有任何一条直接断言 `is_retryable(1045) is False`。也就是说，「1045 不重试」这个承诺现在只有间接证据，没有直接证据。补一条单元测试就能钉死，成本很低。

### 2. CI 上红、本地绿，查了很久

`/history` 在 CI 上偶发 `ConnectionResetError (104)`，本机反复跑都复现不出来。

第 2 次运行（`78eaaae`）：`/history` 裸奔，请求直接撞上 RST。

第 3 次运行（`b5f1e0e`）：加了 try/except，但加在 `/history` 上——**守错了门**。RST 是从 `/ask` 那条连接冒出来的，`/history` 只是捡了一条已经被服务端废掉的 keep-alive 连接，请求根本没走进 `history()` 的函数体。

第 4 次运行（`5c3d922`）才绿：把 try/except 放到 `/ask` 的数据库异常上。

之后做了 20 轮对照实验（8010 端口、错误密码、同一个 Session 连发 20 轮），结果 20/20 都是 500、一次 RST 都没踩中。**结论：这是竞态，不是必现；本地抽不到不等于没有 bug，只等于这一次没抽到。**

### 3. autouse 清库 fixture 让单元测试也要连库

`conftest.py` 里有 `autouse=True` 的清库 fixture，保证每条接口用例开头是干净数据。副作用是两条纯逻辑的单元测试（`is_retryable`、`retry_call`）也被迫每次连一次 MySQL。

评估后决定接受：25 条里只有 2 条受影响，代价是一条连接，收益是不用维护第二套 fixture。**同时记下升级条件**——CI 偶发不稳、或单元测试超过 5 条时，加一个 `@pytest.mark.no_db` 把这两条摘出来。

### 4. CI 第一次红：`requirements.txt` 根本没上去

第 19 天第一次 push，`Install dependencies` 两秒就挂，报 404。原因不是文件写错，是**本地那三个提交从没 push**——GitHub 上那个仓库里压根没有 `requirements.txt`。

一句话：**commit ≠ push。** 本地有文件、本地跑得通，跟远端仓库里有没有，是两件事。

同一批准备里还有两个前提。**第 19 天七次 run 里，这两个没有单独红过**——它们是写 workflow 时一次性做对的：

- `SERVICE_DIR` 用 `Path(__file__).resolve().parent.parent / "service"`，不写死 `D:\Code\fastapi-learn`——CI 上没有 D 盘
- 加 `service/init_db.py`（`Base.metadata.create_all`）——CI 的 MySQL 容器是空库，有库名没表

这三件事的共同点：**本地成立的东西，换到一台干净机器上不成立。**

### 5. `python -m pytest` 里的 `-m` 不是可有可无

`conftest.py` 顶部写着 `from service.database import SessionLocal`。裸 `pytest` 跑会 `ModuleNotFoundError`，因为 `sys.path` 里没有仓库根。`-m` 的作用就是把当前目录（仓库根）加进去。

这条改起来很便宜，但不知道为什么就改不动——报错看着像「包没装」，实际是「路径没进去」。

### 6. 少了 cryptography，MySQL 8 连不上

`pymysql` 是纯 Python 驱动，但 MySQL 8 默认认证插件是 `caching_sha2_password`，握手需要 `cryptography` 做加密。`requirements.txt` 漏了它，pymysql 会直接报「这个包是 sha256 认证所必需的」——报错点名缺包，不是连接被拒。

## 三、阶段二将接什么

> 以下全部是打算，不是已完成的成绩。

**评测层**：接 AI 评测，六个维度——知识点正确性、步骤一致性、超纲检测、讲解分层是否匹配学生水平、多轮对话稳定性、幻觉率。每维至少 2 条用例，先把前两维跑通，其余边跑边补。

**裁判**：LLM-as-Judge 的最小实现。裁判按 rubric 打分、强制返回结构化 JSON，先只做一个维度，跑通一条就是跑通全部。

**证据**：每条维度至少留一条失败佐证，形式是三样之一——仓库内的失败用例、Trace 日志、Judge 误判报告。

**节奏**：1 月底冻结六个维度；2—3 月只补对抗用例，不新增维度。维度一改，历史分数就不能比了。

**边界**：阶段二只新增 `eval/` 目录，不改服务层代码。

## 四、已知限制

**1. 超时的接口层验证只在手工脚本里，没进测试用例。**

`resilience.md` 里那组 500 / 5.13 秒的数据，是 2026-11-17 用一个临时模块测出来的（放在 `%TEMP%`，没碰仓库）。做法不是改 `database.py`，而是：

- 先把 `database.SessionLocal` 整个换成一个指向**黑洞地址 `10.255.255.1`** 的 `sessionmaker`（那个 engine 带 `connect_timeout=5`）
- **换路标必须在 `import main` 之前**——因为 `main.py` 里写的是 `from database import SessionLocal`，导入顺序一反，`main` 拿到的还是原来指向 localhost 的那个，实验等于白做
- 再 `uvicorn bad_db_app:app --port 8001` 起起来，掐表发一条 `/ask`：500，5.13 秒

**注意别把它和第二节那条「错误密码起 8001」混成一件事。** 两次实验都用了 8001 端口，但机制和结论完全不同：错误密码是 **1045**（对面明确拒绝，几十毫秒，验的是 fail-fast）；黑洞地址是 **2003**（对面沉默，等满 5 秒超时，验的是超时上限）。

它没进仓库，所以意味着：有人把 `connect_timeout` 从 5 改成 30，**没有任何东西会变红。**

**2. 单元测试继承了 autouse 清库 fixture。**
每条多一次 MySQL 连接。升级条件见 `test-design.md`。

**3. 服务层不接 LLM，评测层未开始。**
`/ask` 是「题库匹配」不是「模型生成」。学生问题库外的题只能得到「暂未收录」。这是刻意的——有标准答案才能练评测。

**4. `_CACHE` 是进程内字典。**
服务重启就忘，多进程各存各的，扩容多机直接失效。数据库唯一索引是持久的那一层，所以重启后能查到「这个 id 来过」，但没有旧答案可返回。

**5. `seed.py` 不幂等。**
它没有查重，跑一次插五条。实测过一次：`questions` 表 15 条、只有 5 种内容，同一份题库被插了三份（id 1—5、11—15、16—20），已清回 5 条。改法留到阶段二扩题库时一并做——那时本来就要重写这个文件。

**6. 「1045 不重试」没有直接断言。**
25 条里没有一条 `assert is_retryable(OperationalError(1045, ...)) is False`，接口层的 `elapsed < 6` 又抓不住它。这条现在靠设计保证，不靠用例保证。补一条单元测试就能钉死，但不在冻结前夜动手——记在案，阶段二开工前补。

## 一条合格的坑要有什么

| 栏 | 要求 |
|---|---|
| 用例 | 能在 `eval/cases/*.json` 里搜到的 ID；没有用例的，指明能复现的入口（如 `python -m eval.judges.knowledge`） |
| 输入与答卷 | 题面、标准答案、喂进去的答卷，三者缺一不可 |
| 期望判定 vs 实际判定 | 档位和理由都要写，只写「判错了」不算证据 |
| 根因 | 说清是 prompt 没约束住、取数取错了、还是规则覆盖不到 |
| 修正 | 已经改的写改法，没改的写打算怎么改 |
| 佐证文件 | 仓库里能翻到的那份文件 + 哪一节 |

## 坑 1：判分器的理由自相矛盾，还指错了位置

- **用例**：`eval/judges/knowledge.py` 的 `__main__` 自检块（`demo_case`，`id=demo`），入口 `python -m eval.judges.knowledge`
- **输入**：题目「一个数的 3 倍加 2 等于 8，求这个数」；标准答案 `2`
- **答卷**：`设这个数为 x，3x+2=8，3x=6，x=3。所以这个数是 3。`（故意喂错）
- **期望判定**：`partial` / `final_answer_error`——方法对、最后一步抄错
- **实际判定**：档位判对了（`partial` / `final_answer_error`），理由却是「得数正确，但中间步骤 3x=6 的计算错误，应为 3x=6，x=2」
- **两处错**：
  1. **自相矛盾**：先说「得数正确」，可答卷给的 3 跟标准答案 2 不相等，得数本身就是错的
  2. **指错位置**：`3x=6` 这一步没错，错在两边除以 3 时该得 2 却写了 3
- **根因**：`JUDGE_SYSTEM_PROMPT` 里三档定义写的是「得数对但定理用错」「得数错且过程也错」，判分器没有逐条比对答卷，而是按档位定义拼了一句话；「得数正确」是套话，后面那句是为了凑 `partial` 硬加的
- **修正（未做）**：rubric 里加硬约束——`reason` 必须点名答卷里的具体一行或一个数，禁止复述档位定义；说不出来就降档
- **佐证文件**：`docs/ai-eval-notes.md` 第六节「判分器自检的第一次观察（2026-11-25）」

## 坑 2：两道不同的题，判分器会间歇性地给同一句套话

- **用例**：`eval/cases/knowledge.json` 里的 `g7-eq-003` 与 `g7-eq-004`
- **输入**：
  - 003：两位数应用题（个位十位之和为 6，对调后新数比原数 3 倍多 6），标准答案 `15`
  - 004：同类项判定（`(1/4)a^(x+1)b^4` 与 `9a^(2x-1)b^4` 之和仍是单项式），标准答案 `x=2`
- **期望判定**：两条都 `pass`，但理由应各自说各自的题
- **实际判定（两次方向相反的观察）**：
  - 第 25 天第二次连跑：两条 `reason` **一字不差**——「得数正确，引用的定理、公式名称也对」；而 003 是自编应用题，全程没引用任何定理
  - 第 26 天重构分派表后再跑：两条**不再相同**——003「所有步骤正确，方程列得准确，计算无误」，004「得数正确，引用的定理、公式名称也对」
- **所以这条要改口径**：它是**间歇性**现象，不是稳定复现的缺陷。同一个毛病，但验收时只跑一遍很可能看不见。
- **根因**：`reason` 在复读 rubric 的档位定义。rubric 里 `pass` 的定义恰好就是那句套话，判分器有时直接把定义抄成理由，题面差异被吞掉。`temperature` 虽为 0，但不是逐字确定的——输入长度、上下文不同，措辞会漂。
- **修正（未做）**：同坑 1（点名具体步骤）；另加「证据字段」，要求理由里带答卷原文的一句，照不出来判 `partial`
- **验收点**：**连跑两遍**，`g7-eq-003` 与 `g7-eq-004` 的 `reason` 在任何一遍里都不该相同；连续两遍都撞见才算没修
- **佐证文件**：`docs/ai-eval-notes.md` 第七节「四条用例连跑三次的稳定性观察（2026-11-25）」；第 26 天那次的反例目前只在 `eval/results.json`（运行产物，不进版本库），复盘时并入 `docs/ai-eval-notes.md`

## 坑 3：同一处缺陷，压缩连写的答卷被判宽，分步编号的被判严

- **用例**：`eval/cases/step_consistency.json` 里的 `sc-001` 与 `sc-004`
- **输入**：同一道题——「已知 x=-2 是方程 8-ax-b=3-2x 的解，求 3-4a+2b 的值」；标准答案 `5`；题型 `calc`
- **答卷（同缺陷，只差排版）**：
  - `sc-001`：`把 x=-2 代入方程，得 8+2a-b=3+4，即 2a-b=-1。把这个式子代进目标式，算得 3-4a+2b=5。`
  - `sc-004`：同样不写 `3-2(2a-b)` 这个变形，只写「将 2a-b=-1 整体代入目标式」就跳到 `5`，但用「第一步／第二步」分步编号、单独成行、带 `∴` 和加粗标记
- **期望判定**：两条都应 `partial / skipped_calc_step`——都缺了「把 -4a+2b 改写成 -2(2a-b)」这步关键变形
- **实际判定（各连跑两遍，结果一致）**：
  - `sc-001` → `pass / null`。两遍理由都把变形替它写了出来：「代入目标式（即 3-2(2a-b)=3-2(-1)=5）得到 5」。答卷里没有这行。
  - `sc-004` → `partial / skipped_calc_step`。两遍理由都准确：「缺了关键变形：写成 3-2(2a-b) 再代入 -1 得 3-(-2)=5，这一步计算未写出」
- **原预设没有踩中**：建档时预判坑 3 是「同一份答疑换排版，Judge 给出不同判定，根因是把格式工整当成逻辑正确」。实测方向相反——**排版工整的那条判得准，压缩连写的那条判宽**。差别不在「好不好看」，在「有没有可对账的锚点」。
- **根因**：分步编号给了裁判逐条对账的锚点，缺哪步能直接指出来；压缩连写的答卷被读成一个完整意图，而不是一笔可查的账。`算得 3-4a+2b=5` 里的「算得」是个黑箱动词——后面直接跟结果，中间过程没出现，但裁判读成「它做了这个变形，只是没展开」，于是自动补齐。原有约束「不许替答卷补步骤」管不住它，因为裁判并不认为自己在补。
- **修正（已做，两处）**：① `step_consistency.py` 的 prompt 在「只判答卷实际写出的内容」之后加一条——压缩连写的叙述必须先拆成隐含的最小步骤序列再逐条对照，每个变形/代入必须在这句话里显式出现才算写出，「代进某式」「算得」「即得」「由此得」后面直接跟结果一律算缺步。② **把原第 36 行「只有一句话但结论正确、过程确实不需要展开可以判 pass」收紧**为「整题只需一步计算、且这一步本身不可再分」，并写明题需两个以上变形动作时不许援引本条。
  - **第②处比第①处更关键**：`sc-001` 恰好是「只有一句话、结论正确」的形态，第 36 行给了裁判一条合乎规则的放行通道。只加拆条规则而留着这条，仍可能判 `pass`。教训是**约束打架时模型永远选宽的那条**。
- **验收结果（2026-11-26 晚，通过）**：四条各跑两遍，两遍完全一致——`sc-001 partial/skipped_calc_step`、`sc-002 partial/skipped_reasoning_step`、`sc-003 fail/unreachable_conclusion`、`sc-004 partial/skipped_calc_step`。`sc-001` 的两遍理由措辞不同但都点名「算得」后直接跟结果，说明是真核对而非背结论。`sc-004` 确立为常驻回归用例。
- **无效方案记录**：「同一条跑三遍取多数」对这个坑无效——稳定错跑三遍还是三遍 `pass`，只能改 prompt。
- **佐证文件**：`docs/ai-eval-notes.md` 8.9 节「排版对照的意外结论：结构清晰反而判得更严（2026-11-26）」
